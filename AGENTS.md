# AGENTS.md

Tower Of HA (ToH) is a suite of NixOS modules that turns a few cheap machines
into one highly available, fully free service stack. A deployment imports the
modules on every machine and picks which services each machine runs. The
direction of the project is in `docs/design.md` and the order of work in
`docs/plan.md`; read both before larger changes, because much of the code is
being reshaped.

## Structure

The repository is a Nix flake built on
[haraspkgs](https://github.com/haras-unicorn/haraspkgs). `flake.nix` calls
`haraspkgs.lib.makeFlake` over `src/nix`, so every `.nix` file there is a
flake-parts module.

- `src/nix/lib/`: pure helpers and types, with their unit tests in the same file
  under `self.unitTests`.
- `src/nix/meta/`: the `toh.meta.*` options, which describe a machine, the
  cluster and the capabilities services offer each other.
- `src/nix/modules/`: one folder per service. `default.nix` is the module,
  `test.nix` its NixOS test, and other files are its assets (Nushell scripts,
  for example).
- `src/nix/overlays/`: packages and package helpers under `pkgs.tohPackages`.
- `src/nix/test/`: shared helpers and modules for the NixOS tests. Under
  `contracts/`, one contract test per capability; each implementation plugs
  itself in from its own `test.nix` (see the design's contract shape).
- `src/nix/cli/`: the base of the `toh` CLI.
- `src/nix/dev/`: the dev shell and the docs package.
- `docs/`: the mdbook.

## Development

The dev shell loads through direnv. It provides one `dev` command:

- `dev format` formats everything.
- `dev check` runs spelling, markdown, `nil` and generated-file checks.
- `dev docs` builds the book, `dev check-links` checks its links.
- `dev test` runs the NixOS tests, see below.

`nix flake check` runs the unit tests and the other checks, but not the NixOS
tests. Evaluating all of them in one process takes tens of GB of RAM, because
each test evaluates several full NixOS machines. So the tests are not flake
checks. Every test builds as `lib.<system>.nixosTests.<name>`, and `dev test`
builds each one with its own `nix` process, so the memory of an evaluation is
freed when its test ends. `dev test --jobs <n>` runs `n` tests at once and
`--filter <regex>` picks the tests whose names match, for example
`--filter 'ceph|samba'`. A test that sets `passthru.skipped = true` is left out
unless `--skipped` is given.

The tests are also memory hungry to run: each one boots several machines with
databases, filesystems and networks. A test that runs out of time under swapping
usually passes on its own. Tests run as containers; one that sets
`toh.test.kind = "vm"` says why in a `NOTE` comment. The CephFS tests, and the
tests of services that keep data on it, need `/dev/fuse` in the host's
`extra-sandbox-paths`, and the VPN tests need `/dev/net/tun`. When a service
needs something a container cannot give (the real clock, a kernel client), the
container test fakes it or uses a workaround, and a skipped VM test covers the
real thing.

## Generated files

The dev shell writes `.gitignore`, `.gitattributes`, `.editorconfig`, `.envrc`,
`LICENSE.md`, `CODE_OF_CONDUCT.md` and `.github/workflows/*` on entry. Their
source of truth is `src/nix/dev/default.nix`; edit that, not the files.
`flake.lock` changes only through `nix flake lock` or `nix flake update`.

## Project rules

- Secrets are generated by cryl from `toh.meta.cryl.*` declarations. The sops
  files of a deployment are the source of truth; nothing else may hold a secret
  that is not in them. Never write a secret into Nix code.
- Services find each other through `toh.meta.*` (endpoints, capabilities,
  readiness targets), not through hard-coded hosts or ports.
- Every service runs on more than one machine. A service that allows only one
  active process gets failover, for example through an etcd lease.
- Only free software, in every closure.

## Workflow

Work happens on a branch in small commits that are reviewed one at a time. CI
runs `dev check`, `nix flake check` and `dev test`.

When a chunk of `docs/plan.md` is done, the plan records what was done, under
that chunk and with the date, in the same change. The plan is the log of what
happened to the work, so it also says when something changed on the way.

### Review phase (temporary)

While `fix/modernize` is in its big-changes phase, the human skims the log and
the diffs instead of reviewing every line. A skim checks only two things: that
the tests really run, and that nothing reaches the internet when it should not.
Once the shape of most things is settled, careful review starts, in rounds of
review and fix until the human is satisfied. Remove this section then.
